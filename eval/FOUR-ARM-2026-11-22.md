## 1. 四臂定义（计划书 §12.1）

| 臂 | 配置 | 作用 | 执行环境 |
|---|---|---|---|
| L0 原生 | 无插件，standard preset | 基线 | **真机**（离线不可跑：需宿主 + 真模型） |
| L1 PTC | 仅 PTC preset，无本插件 | 对照：code-as-action | **真机** |
| L2 标准通道 | 本插件 + standard preset，通道=标准 | 无代码通道路径 | 真机（主）+ 离线结构（辅助） |
| L3 代码通道 | 本插件 + PTC preset，通道=代码 | 核心实验臂：同 preset，仅变治理 | 真机（主）+ 离线结构（辅助） |

任务集：10 个既有任务 + 4 个长任务（15/30 回合量级）+ 2 个大文件任务（>2,000 行）。判据：

- **H1**：L3 与 L1 在 `|ΔN| ≤ 1` 的成对样本上，总 token 低 ≥15%，且 10 个任务中 ≥7 个成立。
- **H2**：L2 的上下文增长斜率 ≤ L1 的 1/3；交叉点 ≤6 回合。
- 成对比较纪律（§5.8）：`|ΔN| > 1` 的样本视为不可比，单独列出。

## 2. 指标定义（§12.2）

| 指标 | 定义 | 用途 |
|---|---|---|
| `N` | 请求数 | 一等指标 |
| `tokens_total_strict` | `input + output`，不含 `cacheRead` | 严格口径（结论用） |
| `tokens_total_with_cache` | 含 `cacheRead` | 参考口径，不得单独用于结论 |
| `C_max` | 单请求最大上下文 | 增长阶证据 |
| `cache_hit_ratio` | `cacheRead / input` | 换基成本证据 |
| `rebase_count` | 换基次数（计划性 / 非计划性分列） | 前缀策略证据 |
| `verify_pass_rate` | 验收项通过率 | 质量约束 |
| `channel_source` | `preset` / `bridge` / `none` / `standard` | 归因前提 |

硬规则：任何对外结论必须同时给出两个口径（0.4.x 的 28.9% vs 134.9% 教训）。离线跑批没有真 cacheRead 语义，`tokens_total_with_cache` 仅供管线核对。

离线结构结论（仅管线级，非成本结论）：

1. **装配可用**：四臂的 channel/tier/codeSource 判定、度量字段（N / strict / with_cache / C_max / rebase_count / channel_source）在真实驱动器上全部产出。
2. **通道差异可见**：L3 的 C_max 显著低于 L2（代码通道协议段 0 字符 / 200 字符 vs 完整协议段 ≈3.1k 字符）——方向与 §5.7 成本模型一致；`|ΔN| ≤ 2`，成对样本结构可比。
3. **不可比样本纪律**：T3 的 `ΔN = −2`（L3 用一个 run_code 程序替代三次逐轮读取）——按 §5.8 应标"不可比"（N 差异是设计差异：逐轮 vs 单程序），真机报表中单独列出。

## 4. 真机臂执行清单

### 4.1 一条命令跑完四臂（已就绪）

四臂 = 同一 headless profile 上的四个 patch 覆盖层：

| 臂 | patch | 形态 | 装配实测（2026-11-23） |
|---|---|---|---|
| L0 | `patches/eval-baseline.yml` | 原生 loop，无插件 | 可挂载 |
| L1 | `patches/eval-ptc.yml` | PTC 执行器，无插件 | 可挂载（走到凭据墙） |
| L2 | `patches/eval-stream.yml` | 本插件 · 标准通道 | 可挂载 |
| L3 | `patches/eval-stream-ptc.yml` | 本插件 · 代码通道（`channel=code`、`codeChannelSource=preset`） | 可挂载（走到凭据墙） |

```bash
# 真机跑批（需要 DEEPSEEK_API_KEY）
DEEPSEEK_API_KEY=... node eval/tools/four-arm-real.mjs --stamp 2026-11-24

# 已有批次只聚合、不重跑
node eval/tools/four-arm-real.mjs --from-run 2026-11-24

# 只重算判据（改了口径或修了数据时）
node eval/tools/four-arm-real.mjs --recompute eval/runs/four-arm-2026-11-24.json

# 只打印将要执行的命令（零请求）
node eval/tools/four-arm-real.mjs --plan
```

判据实现：`eval/tools/four-arm-verdict.mjs`（纯函数 + `--selftest` 算术自检）。产物：`eval/runs/four-arm-<stamp>.json`（schema `four-arm-real/1`，含 `verdict.h1` / `verdict.h2`），发布门禁 G5 直接消费该文件。

### 4.2 装配层的两条硬约束（实测，已写进补丁注释）

1. **执行器单槽**：base 已声明 `tool-executor-native`（启用）与 `tool-executor-ptc`（停用）。PTC 臂只能翻这两行的开关，新增同 id 或同槽的行会失败（`Only one tool executor may be registered in each scope`）。
2. **运行时由 base 提供**：`ptc-runtime` 行（`dsh-ptc-runtime-node`）无条件挂载，重复插入会撞服务槽（`service ptcRuntime has been registered`）。执行器 `inject ctx.ptcRuntime`，运行时缺席时启动直接失败，不降级。

### 4.3 当前阻塞（2026-11-23）

本机 `dsh 0.2.2-rc.1` 没有 `deepseek-official` 路由的凭据：`dsh headless --json "..."` 返回 `MISSING_CREDENTIAL`。故四臂真机批未执行，`eval/runs/four-arm-*.json` 不存在，G5 保持 FAIL——这是**预期状态**（缺数据 = 未通过，不允许用历史数据补）。

解除条件：一个可用的 `DEEPSEEK_API_KEY`（或经 web Models 页写入凭据），以及调用预算（4 臂 × 10 任务 × 每任务 5–9 请求）。

### 4.4 任务集覆盖缺口

`eval/tasks/tasks.json` 现有 10 个短任务；§12.1 另要求 4 个长任务（15/30 回合）+ 2 个大文件任务（>2,000 行）。后两组尚未建立：不影响四臂管线可用性，但影响 H2 交叉点的可信度（交叉点只有在长任务上才会显现）。
