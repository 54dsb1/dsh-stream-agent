# v0.6.0 升级方案：请求装配对齐

> **合并说明**：本文的 RA-0 探针、请求装配、TF-PEEK 部分已合并到
> `docs/v0.6.0-plan-ra0-peek-assembly-2026-11-24.md`；后续以该文档为准，本文保留为背景与验收口径来源。
>
> **版本号**：暂定 `0.6.0`（结构性升级；若排期只完成 `host` 模式，可按 `0.5.5` 发布）。
> **读者与用途**：仅面向团队内部（研发 / 评测 / 宿主对接）。本文是排期与验收依据，不是用户说明，不对外发布。
> **基线**：`artifacts-v0.5` 工作区，`@hugesb/dsh-stream-agent 0.5.3-beta`；0.5.4 的两个用户开关尚未实现。
> **对标**：xuxiang-thinkflow `0.10.3`（2026-11）。只参照其**机制与方向**，不引用其绝对数字作门槛——任务集、供应商、计量口径都不同，不能直接相减。
> **标记规则**：`[P0]` 本轮必须完成；`[P1]` 本轮应完成；`[P2]` 可延后。状态只有四种：`待实施` / `待探针` / `阻塞` / `已确认`。

---

## 0. 一句话结论

本轮主要解决一件事：**把"每次请求发什么"的决定权，从宿主历史累积改为插件可计算的装配计划**。
拿不到这个权力，插件现有的节省上限是"不产生内容"，而不是"不发送内容"；对齐 thinkflow 只能停在协议层，进不到装配层。

---

## 1. 目标与判定口径

### 1.1 主目标

`AssemblyPlan` 成为请求内容的唯一事实源：system 块、messages 投影、tools 声明、reasoning 策略、发送前预算，全部由插件计算并可复算；宿主只做校验与发送。

**"通过插件"的三层边界**：

| 层 | 内容 | 本轮 |
|---|---|---|
| L1 插件独立 | 协议段、工具声明、载荷去重、确定性压缩、发送前预算、同轮交付 | 直接做 |
| L2 宿主接缝 | system 整块替换、messages 裁剪/投影、tools 置空、reasoning 策略 | RA-0 探针后做 |
| L3 宿主改造 | 请求字段级完全装配、provider 参数控制 | 本轮不做，不 fork |

### 1.2 "对齐 thinkflow 效果"的操作化定义

不比较绝对 token，只比较**可观测的装配不变量**。每条都必须能在请求体或账本上断言。

| # | thinkflow 的效果 | 插件侧可观测断言 | 验收数据源 |
|---|---|---|---|
| A1 | 默认文本协议，不为原生 tools schema 付每请求 token | 请求 `tools` 字段缺失或为空；`toolsChars=0` | eval-probe 请求原文 |
| A2 | 工具按需加载（首请求 14→7） | 首请求声明的工具名 ≤7；其余工具可按名调用；完整 schema 按需取 | 请求原文 + `AssemblyPlan.tools` |
| A3 | 只追加变化状态，不重复写同一状态 | 同一状态块的 `sha256` 在单请求中出现 1 次；每回合新增状态块 ≤1 | 请求体扫描 |
| A4 | 成功载荷只保留一份，重复读给引用 | 大于 2,000 字符的载荷，同 `sha256` 在单请求中出现 ≤1 次；重复读返回 `[unchanged]` 或 `[ref:xxxxxxxx]` | 请求体扫描 + 账本 |
| A5 | 压缩不额外调模型，原文可回取 | 压缩期间新增 LLM 调用 = 0；压缩后原文句柄回取成功率 100% | 请求计数 + 回取测试 |
| A6 | 同轮交付，不因缺 final 多一次请求 | 无 `tf-final` 的正常回合，请求数不增加 |暂时不做API验收 |

### 1.3 数字门槛（10 题任务集，同模型、同 key、同日、两臂）

计量口径沿用 `eval/METRICS.md`：四分量 = 未缓存输入 + 缓存读 + 缓存写 + 输出；严格二分量 = 未缓存输入 + 输出。

| 门槛 | 条件 | 判定 |
|---|---|---|
| G1 | 严格二分量 ≤ 基线 ×1.00 | 必须通过 |
| G2 | 四分量 ≤ 基线 ×1.00 | 必须通过；仅 G1 过而 G2 不过时，只允许 opt-in，不得默认 |
| G3 | 请求数 ≤ 基线 | 必须通过 |
| G4 | 前缀违规 = 0 | 必须通过 |
| G5 | 任务成功率 ≥ 基线 | 必须通过 |
| T1 | 未缓存输入 ≤ 基线 ×0.70 | 对齐目标（参照 thinkflow 同向降幅 −34.69%），未达不阻断，但需 gap 分析 |
| T2 | 总 token ≤ 基线 ×0.85 | 对齐目标，未达不阻断 |

**纪律**：失败与超时任务照常进分母；两臂 runner 参数除装配补丁外逐项相同；任何数字必须能从 probe log 重算。

### 1.4 基线冻结（M0 前置）

- 冻结 `0.5.3-beta` 的可运行产物与 commit hash；`nativeTools=false`；全部 `limits` 未设（0）。
- 先跑一轮 10 题基线并归档：`eval/runs/baseline-0.5.3/`。
- **当前没有 0.5.x 真机 token 数字**，这一轮基线是本轮所有判定的唯一分母；不得用 0.4.x 历史批次替代。

### 1.5 本轮不做

- 不改宿主源码、不 fork dsh；只使用现有插件接缝与宿主配置。
- 不改 provider 协议；不增加任何"为省 token 而多调一次模型"的机制。
- 不重写 `tf-*` 协议语法；RA-3 只新增一个按需 schema 命令。
- 不写用户文档与发布说明；本文件只作团队排期与验收依据。
- 不做涵盖API的验收和测试。

## 2. 现状与结构缺口

| 请求字段 | 现在谁决定 | 插件能否改 | 后果 |
|---|---|---|---|
| system | 插件写自己的段，宿主可再包一层 | 只能追加，不能删除宿主段 | 宿主技能目录/包装提示每请求都付费 |
| messages | 宿主从 session 事件投影 | 只能 `surfaceOp:'append'`，`replace` 未验证 | 历史只能增，不能改写、删除、重排 |
| tools | 宿主按会话工具面装配 | 插件默认不发 schema，但宿主是否补回未验证 | 可能一边省 schema，一边被宿主加回 |
| reasoning | 插件随 assistant 消息落 `reasoning` 块 | 是否回传由宿主/provider 决定 | 旧推理可能每请求重复发送 |
| 工具结果 | 插件在写入前决定注入多少 | 已写入的历史无法在发送前替换 | 大结果一旦进历史，只能靠压缩整块丢弃 |

结论：**插件的节省发生在"写入前"，thinkflow 的节省发生在"发送前"。** 本轮补的就是这一段。

## 4. 关键项：请求装配（RA）

### RA-0 宿主装配接缝探针 `[P0][探针][阻塞]`

**目的**：先确认宿主是否允许插件参与发送前装配。不确认就写代码，等于赌宿主行为。

**探针清单**（每项一份产物，含 3 个连续请求的原文 diff）：

| 探针 | 问题 | 若"不支持"的影响 |
|---|---|---|
| U1 | `llm/stream` 的 messages 是否可与 session 投影不同（裁剪/替换/重排） | RA-2 只能走"不产生"路线，收益上限下降 |
| U2 | `tools` 字段能否由插件置空或裁剪，宿主是否补回 | A1/A2 不可保证 |
| U3 | `reasoning` 块是否必须原样回传（DeepSeek thinking） | 旧推理无法省略，只能靠单流减少回传次数 |
| U4 | `systemPrompt.context` 是替换还是追加；多次注入是否累积 | 固定前缀无法收敛 |
| U5 | `surfaceOp:'replace'` 是否真被宿主接受并影响下一请求 | 历史改写不可行，RA-1 降级为 append-only |
| U6 | 请求头/usage 是否暴露逐请求 cache 字段 | MT-1 只能估算，G1/G2 可信度下降 |

**落点**：`eval/runs/ra0/<probe>.json`；每个文件必须写 `verdict: supported | unsupported | unknown` 与证据行号。
**验收**：6 项全部有明确结论；`unknown` 不得超过 1 项；不支持的项当日写入 `docs/limitations.md`。
**回退**：U1 或 U5 不支持 → RA-2 缩为"源头减量"子集，`plan` 模式不发布，只保留 `host`。

---

### RA-1 `AssemblyPlan` 契约与 dry-run `[P0][核心]`

**契约形态**（字段名可调，语义不可减）：

```ts
interface AssemblyPlan {
  system: { blocks: Array<{ id: string; text: string; stable: boolean }>; hash: string };
  messages: Array<{ role: 'system' | 'user' | 'assistant'; content: string; ref?: string }>;
  tools: null | Array<{ name: string; description: string; parameters: unknown }>;
  reasoning: 'provider-required' | 'drop-stale';
  budget: { estimatedInputTokens: number; limit: number; overBy: number };
}
```

**实现要求**：

1. 纯函数：输入 `AssemblyState`（任务、账本、载荷库、limits、通道），输出 `AssemblyPlan`；不读时钟、不读网络。
2. 同一状态连续投影 20 次，逐字节一致；块顺序固定：`channel → protocol → tools → invariants → state`。
3. dry-run 模式只落 `assembly.plan.json` 与 `assembly.diff.json`，不改变发送内容；diff 只允许出现预期字段。
4. `AssemblyPlan` 与 `surfaceOp:'replace'` 只能有一个事实源：若 U5 支持 replace，则 plan 只做内容计算，replace 只做投递；若 U5 不支持，plan 只做 append 增量。

**落点**：新增 `src/kernel/assembly.ts`（类型与纯函数）、`src/entry/assembly-dryrun.ts`（入口）、`eval/tools/assembly-dryrun.mjs`（批跑）。
**验收**：
- 契约文档 + 20 次投影逐字节一致；
- dry-run 与真实请求逐字段 diff，除允许字段外 0 差异；
- 前缀违规 0；
- 现有 `npm test` 全绿，发送路径行为不变（A/B 请求体 hash 相同）。

**回退**：`assemblyPolicy='host'` 时完全不进 plan 构建，逐字节回到 0.5.3。

---

### RA-2 内容寻址载荷库与历史投影去重 `[P0][核心]`

**目的**：对齐 A3/A4——同一份成功载荷只保留一份；重复读给引用；压缩后可回取。

**做法**：

1. 载荷库：`sha256(bytes)` → `{ handle, bytes, firstSeq, refs[] }`；只在首次注入时进上下文。
2. 装配投影：已在历史中的载荷不再重复注入；需要时给 `[ref:<sha8>]`，模型用 `tf-peek handle=...` 取回。
3. 若 U1/U5 不支持改写：退化为"源头减量"——大文件走 code 通道在程序内处理，只注入结论；`tf-read` 全文只在"本任务确实要逐行看"时注入一次。
4. 压缩保持确定性：纯函数摘要、每条 900 字符、保留最近 N 条；压缩不调模型；原文句柄保留。
5. 原生工具结果：`nativeTools=false` 时不再产生新结果；历史里已有的大块结果只做引用投影（需 U1/U5）。

**落点**：新增 `src/kernel/payload-store.ts`；改 `src/entry/loop.ts` 的 read / native result / compaction 三处注入点；账本新增 `payload_first_seq` 与 `refs`。
**验收**：
- 请求体扫描：>2,000 字符载荷同 sha 出现 ≤1 次；重复载荷字节占比 ≤5%；
- 重复读 10/10 返回 `[unchanged]` 或 `[ref:]`，不返回全文；
- 压缩后 20/20 句柄可回取，内容 sha 一致；
- 10 题：G1–G5 全过；T1/T2 如实报告。

**回退**：`payloadProjection=false` → 回到 0.5.3 的"每次读都注入、压缩整块丢弃"。

---

### RA-3 工具惰性声明与按需 schema `[P2][工具面]`

**现状**：插件默认 `nativeTools=false`，自身不向请求添加 `tools` schema；宿主是否另带自己的工具面尚未验证（U2）。因此这里的目标不是"从 14 减到 7"，而是**保证插件侧不新增 schema，并把可用工具名压到最小集合**；宿主侧的部分由 U2 结论决定能否裁剪。

**做法**：

1. 首请求只声明 6 个核心入口：`read / write / edit / bash / python / load_tools`；其余工具按名走 `tf-call`，不列全表。
2. 完整 schema 按需：新增 `tf-schema name=<tool>`，一次只回一个工具的 schema；不写入稳定前缀。
3. 若 U2 证实宿主会补回 `tools` 字段，则改为"请求级裁剪 + 在 plan 中记录被裁项"，并把结论写进 `limitations.md`。

**验收**：
- 首请求 `tools` 为空或缺失，`toolsChars=0`；
- 声明的工具名 ≤7；`tf-call` 调用未列出的宿主工具成功率 ≥ 基线；
- `tf-schema` 单次返回 ≤2,000 字符，且不回灌全表；
- 10 题成功率不低于基线。

**回退**：`lazyTools=false` → 恢复当前"全表按名可调 + 不声明 schema"的行为。

---

### RA-4 发送前预算与 fail-closed `[P1][预算]`

**做法**：

1. 发送前按字段估算：`systemChars + messageChars + toolsChars`，按 `/4` 折算 token；与 `maxInputTokens` 比较。
2. 超限先做确定性压缩与计划性换基，再复算；仍超限则**不发送**，输出 `[tf-stream:budget]`，列出前三贡献项（system / messages / tools / reasoning）。
3. 不允许"先发出去再压缩"；不允许半截前缀；预算拒绝要可被用户看见。

**验收**：
- 50 组故障注入（system 过大、单条消息过大、工具 schema 过大、压缩后仍超限）：超限发送 0 次；
- 每次拒绝都有 `[budget]` 文案与贡献项；
- 拒绝不增加请求数；下一回合可正常继续；
- 不产生前缀违规。

**回退**：`preSendBudget=false` → 只告警不拒绝（当前行为）。

---

### RA-5 `assemblyPolicy` 与自动回退 `[P1][回退]`

**做法**：

1. `assemblyPolicy: 'host' | 'plan'`，来源优先级：装配 config > 环境变量 > `control.json`。
2. 0.6.0 默认 `host`；`plan` 仅在 M2 门禁通过后允许 opt-in，是否默认由团队决策（见 §9）。
3. `plan` 构建或宿主校验失败时，自动回退 `host`，记录 `assembly-fallback` 事件（原因、阶段、请求序号），任务不中断。

**验收**：
- 回退后的请求体与 0.5.3 逐字节一致（10 题、逐请求 hash）；
- 注入 20 次 plan 失败（构建异常、宿主拒绝、字段缺失）：20/20 回退成功，0 任务失败；
- 回退事件可在账本中检索，含原因与序号；
- `host` 模式下 plan 代码零执行（覆盖率断言）。

## 5. 配套项

### MT-1 逐请求装配账本 `[P0][计量]`

**做法**：每请求一行 JSONL：

```json
{"seq":1,"policy":"plan","systemChars":2100,"messageChars":8400,"toolsChars":0,
 "reasoningChars":1200,"estimatedTokens":3000,"prefixHash":"...","cacheRead":0,
 "cacheWrite":0,"input":2900,"output":300,"rebase":null}
```

**验收**：与 eval-probe 的 usage 对账误差 ≤0.5%；10/10 任务账本完整；缺字段标"不可得"，不按 0 计。

---

### CF-1 `contextFold` 用户开关 `[P1][开关]`

**语义**：总开关，控制"压缩 + 效果折叠"是否允许发生；不控制 `segmentMaxChars` 段边界。
**映射**：`false` → 强制 `surfaceCompaction=false` 且 `effectElisionKeepRecent=0`；`true` → 沿用用户 limits，未设阈值时显示"已开启，未设阈值，不触发"。
**验收**：4 种组合（开/关 × 阈值设/未设）各跑 10 回合；关闭时压缩事件 0、压缩型换基 0；开启且设阈值时压缩触发且 `[context-rebased]` 可见；控制台显示有效状态而非仅开关值。

---

### FC-1 `finalCheck` 用户开关 `[P1][开关]`

**语义**：只控制"流末验收与收束"，不控制 plan 段。
**映射**：`false` → 不要求 `tf-final`、不判 `accepts`、不做收束 nudge；`tf-plan` 仍解析。代码通道当前无验收闸，控制台置灰。
**验收**：`enablePlan` × `finalCheck` 2×2 矩阵各 5 回合；关闭时请求数不增加、无孤立 `tf-final` 报错；开启时未完成交付返回 `blocked` 或未完成说明；代码通道开关不可点。

---

### PF-1 前缀 fail 零产出回合兜底 `[P1][兜底]`

**问题**：当前 fail-closed 后，若该回合零产出，不写 `[未完成交付]` 事实消息，下一回合模型不知道发生过失败。
**做法**：零产出也写一条事实消息（原因、已记账的 pending 意图标 `unknown`、建议下一步），不重放、不自动重试。
**验收**：注入 `stable-drift` / `shrink` / 超预算三类 fail，各 5 次；15/15 有兜底消息；请求数不增加；下一用户消息可正常续跑。

---

### PK-1 `tf-peek` 预算与命中率 `[P2][取回]`

**现状**：锚点默认每 200 行一个，且窗口内优先取顶层符号（`obs.ts` / `renderReadIndex`）；`tf-peek` 已支持 `from_line/to_line`、`offset`、`query`、`symbol`，query 未命中会明确回报，不当作命令失败。
**做法**：锚点间隔可配（大文件可降到 100 行）；query 未命中时返回 top-3 候选行段，而不是只提示去 grep；句柄记录文件 `mtime+size+sha`，外部改动后返回"已过期"而不是旧文；预算耗尽时明确拒绝，不静默截断。
**验收**：20 个大文件查询；首次命中目标行段 ≥80%；过期句柄识别 100%；预算拒绝 100% 有文案；peek 次数不高于基线。

---

### X-1 同任务跨栈对照（可选） `[P2][对照]`

**目的**：给"效果对齐"一个外部参照，而不是只与自己比。
**做法**：同一 10 题、同模型、同日，分别跑 plugin（`plan`）与 thinkflow `0.10.3`；逐任务记录请求数、未缓存输入、总 token、成功率。
**纪律**：只作参考，不作发布门槛；thinkflow 跑不动的任务标 `n/a`，不计入均值；两边计量口径差异必须写在表注里。
**验收**：10 题逐任务三指标齐全（或明确 `n/a`）；差异最大的 3 个任务有原因分析。

## 7. 验收方法（统一执行）

### 7.1 分层

| 层 | 命令/工具 | 覆盖 |
|---|---|---|
| 契约/单测 | `npm test`、`npm run check`、`npm run gate` | plan 纯函数、预算、开关矩阵、前缀断言 |
| 离线 dry-run | `node eval/tools/assembly-dryrun.mjs --tasks eval/tasks/tasks.json --out eval/runs/ra1/` | 投影一致性、字段 diff、前缀字节 |
| 固定轨迹回放 | 30 回合合成轨迹，不调模型 | A3/A4、前缀 30/30、重复块 0 |
| 真机两臂 | eval-probe + `eval/tools/` 现有 runner（本轮新增装配两臂入口） | G1–G5、T1/T2、任务成功率 |
| 故障注入 | `eval/tools/fault-*.mjs`（本轮新增） | 预算、回退、前缀 fail、零产出 |

### 7.2 真机纪律

- 10 题任务集（W1–W3、R1–R4、C1–C3），两臂各自全新 seed，逐字节同一任务文本。
- 同模型、同 provider、同 key、同日跑完；模型/provider 不一致的任务作废重跑。
- eval-probe 两臂同装，fail-open，不改流。
- 失败/超时照算；每个数字可从 probe log 与 session log 重算；不允许挑数据。
- 每项至少 2 次运行，两次都报；不用最好一次。

### 7.3 证据归档

```
eval/runs/<milestone>/
  probe/*.jsonl          # 逐请求 messages + usage 原文
  ledger/*.jsonl         # MT-1 装配账本
  summary.json           # 逐任务四分量、严格二分量、请求数、成功率
  manifest.json          # 任务文本、seed、模型、commit hash
  notes.md               # 异常与失败原因原文
```

### 7.4 判定

- **通过**：G1–G5 全过，且证据完整。
- **有条件通过**：G1/G3/G4/G5 过，G2 不过 → 只允许 opt-in，报告写清缓存结构变化。
- **不通过**：G1 或 G3 不过 → 该装配项不采纳，回退到上一个可用策略。
