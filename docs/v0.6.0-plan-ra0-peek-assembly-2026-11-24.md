# 下一轮计划：RA-0 / TF-PEEK / 请求装配改写


## 0.离线测试现有内容

检查用户开关这一功能是否已经按需完成

| **A1** `[P0][开关]` | 没有 `contextFold` 用户开关。压缩、效果折叠、段边界只能靠 limits 间接控制，关不干净。 | 新增布尔开关，默认开。`false` 强制 `surfaceCompaction=false`、`effectElisionKeepRecent=0`、`segmentMaxChars=0`（旧内容一律不移出请求）；`true` 沿用用户 limits；未设阈值时显示“已开启，未触发”。 | 开/关 × 阈值设/未设 4 组合各 10 回合：`false` 时压缩、折叠、段丢弃事件均为 0；`true` + 阈值时事件 >0 且 `[context-rebased]` 可见；段边界关闭后追加区增长不触发 drop。 |
| **A2** `[P0][开关]` | 没有 `finalCheck` 独立开关。`enablePlan=false` 会连带去掉 `tf-plan` 段，不能当验收开关用。 | 新增布尔开关，默认开。只控制 `tf-final` 要求、`accepts` 判定、premature-final 拦截、收束 nudge；`false` 时 `tf-plan` 仍解析；代码通道当前无验收闸，控制面置灰。 | `enablePlan` × `finalCheck` 2×2 矩阵各 5 回合：`false` 时无 final 仍正常交付、请求数不增加、无孤立 final 报错；`tf-plan` 段仍在；`true` 时未完成返回 `blocked`。 |
| **A3** `[P0][持久化]` | 两个开关没有落盘、迁移、来源诊断；`control.json` schema 仍为 3。 | schema 升 4，新增 `contextFold` / `finalCheck`；默认 `true`；非法值丢弃并告警；旧文件缺字段回默认；写回保留未知字段；优先级 config > env > file > default。 | v3 文件读入 → 两开关默认 `true`；写回 `schema=4`；非法值告警；来源字段正确；未知字段写回后仍在。 |
| **A4** `[P0][同轮续跑]` | 前缀 fail-closed 后回合直接 `blocked`，用户必须再发一条消息才能继续；零产出时连兜底消息都不写。 | 失败后同轮自动续跑：记账 → `renderer.rebase()` + 清空 wire 基线 → 注入 `[tf-stream:prefix-recovered]` 事实块 → 同一回合发下一条请求；每回合最多 2 次；零产出也写事实消息，不要求用户再发。 | `stable-drift` / `shrink` / `append-drift` 超预算各注入 5 次：15/15 在同一次 `runTurn` 内产生后续请求并结束，无 `awaiting:user`；请求数增加 ≤2；pending 意图标 `unknown`、无重复副作用；零产出有事实消息。 |
| **A5** `[P0][账本]` | 自动续跑没有计数、事由、耗尽终态，无法复算。 | 账本新增 `prefix-auto-continue`（turn/step/attempt/cause）与 `prefix-auto-exhausted`；状态面显示本回合剩余次数。 | 每次续跑有且仅有一条记录；次数与配置一致；耗尽后有明确终态；从账本可复算 attempt 与 cause。 |

## 1. 三项的关系

| 项目          | 解决什么                                             | 依赖           | 失败时的影响               |
| ----------- | ------------------------------------------------ | ------------ | -------------------- |
| **RA-0**    | 确认宿主是否允许插件参与发送前装配                                | 无            | 装配只能做“源头减量”，不能改写已发内容 |
| **TF-PEEK** | 取回命中率、过期句柄、预算可观测性                                | 无            | 模型反复取回，抵消装配节省        |
| **请求装配改写**  | 让插件决定每次请求的 system / messages / tools / reasoning | RA-0 的 U1/U5 | 维持现状：只能在写入前省，不能在发送前删 |

结论：RA-0 是装配的开关；TF-PEEK 是装配的配套；装配是主项。

## 2. RA-0：宿主装配接缝探针

### 2.1 目的

用最小探针确认：插件能不能决定“这次请求带什么”。不确认就写 `AssemblyPlan`，等于赌宿主行为。

### 2.2 六项探针

| 探针     | 问题                                                        | 观测点                                     | 不支持时的处置                 |
| ------ | --------------------------------------------------------- | --------------------------------------- | ----------------------- |
| **U1** | `llm/stream` 的 `messages` 是否可与 session 投影不同（裁剪 / 替换 / 重排） | 3 个连续请求的 messages 原文 diff               | 装配降级为 append-only；历史不能删 |
| **U2** | `tools` 字段能否由插件置空或裁剪；宿主是否补回自己的工具面                         | 请求 `tools` 字段与宿主 `request/header.tools` | 放弃“首请求 0 schema”的断言     |
| **U3** | `reasoning` 块是否必须原样回传（DeepSeek thinking 语义）               | 去掉旧 reasoning 后的请求是否被拒 / 降质             | 旧推理只能靠单流减少，不能省          |
| **U4** | `systemPrompt.context` 是替换还是追加；多次注入是否累积                   | 连续 3 次注入后的 system 字节                    | 固定前缀无法收敛，只能控制插件段        |
| **U5** | `surfaceOp:'replace'` 是否被宿主接受并影响下一请求                      | replace 后下一请求的 messages 基线              | 历史改写不可行，RA-2 缩为“不产生”    |
| **U6** | 请求头 / usage 是否暴露逐请求 `cacheRead` / `cacheWrite`            | eval-probe 逐请求 usage 原文                 | 计量只能估算，token 门槛可信度下降    |

### 2.3 方法

- 新增一个仅用于探针的入口（不改生产路径），挂 `llm/stream`，透传不改流。
- 每个探针跑 3 个连续请求；产物含：请求原文、宿主 session 事件、diff、结论。
- 结论只允许三种：`supported` / `unsupported` / `unknown`，每项附证据行号。
- 探针使用 mock provider，不消耗真实 API。

### 2.4 产物与门禁

```
eval/runs/ra0/
  U1-messages.json
  U2-tools.json
  U3-reasoning.json
  U4-system-context.json
  U5-surface-replace.json
  U6-usage.json
  summary.md          # 六项结论 + 对装配路线的影响
```

**门禁**：6 项全部有结论；`unknown` ≤1；不支持的项当天写入 `docs/limitations.md`。

### 2.5 决策树

| RA-0 结论       | 装配路线                                              |
| ------------- | ------------------------------------------------- |
| U1 + U5 支持    | 完整 `AssemblyPlan`：可裁剪、可投影、可改写历史                   |
| 只有 U2 / U4 支持 | 只做 system / tools 裁剪；messages 保持 append-only      |
| U1 / U5 均不支持  | 只做“源头减量”：不产生大块内容、压缩整块丢弃；`plan` 模式不发布              |
| U3 不支持        | `reasoningPolicy` 固定 `provider-required`，不尝试丢弃旧推理 |

## 3. TF-PEEK：取回质量

### 3.1 目标

让模型一次取到目标，不因索引漏行、句柄过期、预算不明而反复 peek。

### 3.2 计划项

| 编号       | 问题                                | 计划                                                                                                         | 验收（离线）                                                 |
| -------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| **PE-1** | `query` 未命中只提示去 `tf-grep`，模型只能盲试  | 未命中返回 top-3 候选行段（行号 + 首行，≤2,000 字符）；候选按查询词命中数排序，不调模型                                                       | 20 个大文件用例：首次命中目标行段 ≥80%；未命中 100% 有候选；响应 ≤2,000 字符      |
| **PE-2** | 行锚固定每 200 行一个，目标容易落在锚点之间          | 锚点间隔可配 `peekAnchorEvery`（默认 200，可设 100）；窗口内仍优先顶层符号                                                         | 间隔 100 时锚点数增加；索引 ≤2,000 字符；不改变默认行为                     |
| **PE-3** | handle 是读取时快照，文件外部改动后仍返回旧文        | `tf-read` 登记 `handle → { path, mtimeMs, size }`；`tf-peek` 前 `stat` 校验；变更返回 `[stale]` + 新 mtime/size + 重读建议 | 改文件后 peek 10/10 返回 `[stale]`；未改文件 10/10 正常；旧文不冒充当前内容   |
| **PE-4** | 预算拒绝文案不含剩余额度；`[unchanged]` 也计正文预算 | 拒绝时给已用/上限/剩余与建议窗口；`[unchanged]` 只计命令数                                                                      | 预算 1,000 字符下连续 peek：超限 100% 有剩余额度；`[unchanged]` 前后预算不增 |

### 3.3 不做什么

- 不做语义搜索、不调 embedding、不为取回额外调模型。
- 不改变 `tf-peek` 的现有参数（`handle` / `from_line` / `to_line` / `offset` / `query` / `symbol`）。
- 不把过期句柄自动重读后静默替换——必须让模型知道内容变了。

### 3.4 顺序

PE-1（命中率）→ PE-3（正确性）→ PE-4（预算）→ PE-2（密度）。PE-2 最后做，避免先改索引形态影响命中率基线。

## 4. 请求装配改写

### 4.1 目标

`AssemblyPlan` 成为请求内容的唯一事实源：system 块、messages 投影、tools 声明、reasoning 策略、发送前预算，全部由插件计算并可复算；宿主只做校验与发送。

### 4.2 不做什么

- 不 fork 宿主、不改宿主源码；只用 RA-0 确认过的接缝。
- 不改 provider 协议；不增加“为省 token 多调一次模型”的机制。
- 不在本轮做用户文档与发布说明。

### 4.3 契约

```ts
interface AssemblyPlan {
  system: { blocks: Array<{ id: string; text: string; stable: boolean }>; hash: string };
  messages: Array<{ role: 'system' | 'user' | 'assistant'; content: string; ref?: string }>;
  tools: null | Array<{ name: string; description: string; parameters: unknown }>;
  reasoning: 'provider-required' | 'drop-stale';
  budget: { estimatedInputTokens: number; limit: number; overBy: number };
}
```

约束：纯函数；同一状态连续投影 20 次逐字节一致；块顺序固定 `channel → protocol → tools → invariants → state`。

### 4.4 阶段

| 阶段       | 内容                                  | 依赖         | 验收（离线）                                                    |
| -------- | ----------------------------------- | ---------- | --------------------------------------------------------- |
| **RA-1** | 契约 + 纯函数投影 + dry-run（不改变发送）         | RA-0       | 20 次投影一致；dry-run 与真实请求逐字段 diff，除允许字段外 0 差异；0 前缀违规         |
| **RA-2** | 内容寻址载荷库 + 历史投影去重                    | RA-1；U1/U5 | 请求体扫描：>2,000 字符载荷同 sha 出现 ≤1 次；重复载荷字节占比 ≤5%；压缩后句柄回取 20/20 |
| **RA-3** | 工具惰性声明 + 按需 schema                  | RA-1       | 首请求 `tools` 为空、`toolsChars=0`；声明名 ≤7；未列出工具可按名调用           |
| **RA-4** | 发送前预算 + fail-closed                 | RA-1       | 50 组故障注入：超限发送 0 次；每次拒绝有 `[budget]` 与贡献项；无半截前缀             |
| **RA-5** | `assemblyPolicy: host\|plan` + 自动回退 | RA-1       | 回退后请求体与基线逐字节一致；20 次 plan 失败 20/20 回退；回退事件可检索              |

### 4.5 对齐 thinkflow 的可观测不变量

| #  | 不变量          | 断言                             |
| -- | ------------ | ------------------------------ |
| A1 | 默认文本协议       | 请求无 `tools` 或为空；`toolsChars=0` |
| A2 | 工具按需加载       | 首请求声明名 ≤7；其余按名可调               |
| A3 | 只追加变化状态      | 同一状态块 sha 单请求出现 1 次；每回合新增 ≤1   |
| A4 | 成功载荷只保留一份    | 大载荷同 sha 单请求 ≤1 次；重复读返回引用      |
| A5 | 压缩不调模型、原文可回取 | 压缩新增 LLM 调用 = 0；句柄回取 100%      |
| A6 | 同轮交付         | 无 `tf-final` 的正常回合请求数不增加       |

### 4.6 API 验收（延后）

以下指标需要真实 API，升级完成后另跑，不作为本阶段的通过条件：

- 四分量（未缓存输入 + 缓存读 + 缓存写 + 输出）与严格二分量（未缓存输入 + 输出）；
- 请求数、前缀命中、缓存读写；
- 10 题任务集的逐任务对比。

离线阶段只回答“装配形态是否正确”，不回答“省了多少 token”。
