## 1. 用户开关：`contextFold` 与 `finalCheck`

### 1.1 现状：两个能力存在，但没有面向用户的布尔开关

| 能力 | 现有实现 | 现有开启方式 | 默认实际状态 |
|---|---|---|---|
| 上下文折叠 | 旧段确定性压缩（`kernel/compaction.ts`，`loop.ts` `#maybeCompactForInputBudget`）+ 效果折叠 `[applied pN]`（`effectElision`） | 压缩需 `maxInputTokens > 0`；效果折叠需 `effectElisionKeepRecent > 0` | **均不触发**：两个数值默认都是 `0`（`limits.md`：未设 = 不限制/不折叠） |
| finalCheck | 标准通道 `tf-final` 收束 + `tf-plan`/`accepts` 验收闸 + 四类拒绝 + 占位拒绝 | `enablePlan`（默认 `true`） | 标准通道开启；代码通道本来无 `tf-final`/验收闸（`loop.ts:3116,3152-3175`） |

问题不在“没有能力”，而在“用户要同时理解两个数值键才能控制一个开关”，且 `enablePlan`
同时管计划段与收束校验，无法只关 finalCheck 而保留计划。

### 1.2 定义

#### `contextFold`（上下文折叠）

一个总开关，覆盖两个“把已发生上下文折短”的机制：

| 取值 | 语义 | 等价配置 |
|---|---|---|
| `true`（默认） | 尊重用户在 `limits` 里设的折叠阈值；阈值未设则不触发 | `surfaceCompaction=true`，`maxInputTokens` 按用户值；`effectElision=true`，`effectElisionKeepRecent` 按用户值 |
| `false` | 强制停用旧段压缩与效果折叠；不因压缩产生计划性换基 | `maxInputTokens=0`，`effectElision=false` |

边界说明（必须写进控制台提示，避免误解）：

- `contextFold=true` **不等于一定折叠**。插件纪律是“不预设任何会截断/终止工作的上限”
  （`docs/limits.md` §1），所以 `maxInputTokens` 与 `effectElisionKeepRecent` 仍由用户设；
  两个值都是 `0` 时，开关为开但无实际动作。控制台应显示“已开启，未设阈值，不触发”。
- 任务级 `[tf-budget: …]` 里的 `maxInputTokens` 同样受总开关压制：`contextFold=false`
  时，任务级预算不能重新打开压缩。
- `contextFold` **不控制 F7 段边界**。`segmentMaxChars > 0` 时，追加区超限仍会在新回合
  边界整块丢弃（`loop.ts:2664`）；那是“段边界”，不是“压缩”。控制台需把两者分开标注。
- 关闭后不产生压缩型 `cache-reset`，但 `append-drift` 受限换基仍可能发生（见 §3）。

#### `finalCheck`（收束前校验，即需求中的 finalcheck）

| 取值 | 语义 | 用户可见结果 |
|---|---|---|
| `true`（默认） | 标准通道保留 `tf-final` 收束；`tf-plan` 验收项必须有成功回执；依赖/未完成/验收/占位四类拒绝生效 | 未通过时会被要求收束或补证据；最坏情况是多 1 次 nudge/收束请求，或 `blocked` |
| `false` | 流末正文即交付；不要求 `tf-final`，不做验收闸拒绝 | 可能少 1 次收束请求；但占位、未验证、未完成的内容可能被当成交付 |

实现约束：

- **不能直接把 `enablePlan=false` 当作 `finalCheck=false`**。`enablePlan=false` 会同时
  去掉协议里的 `plan` 段和计划命令（`kernel/protocol.ts:317,338`），而用户可能只想关
  收束校验、保留计划。实施时需把“最终校验”从 `enablePlan` 中拆成独立判定点。
- 代码通道当前没有 `tf-final` 与验收闸，`finalCheck` 在代码通道下应置灰并标注“该通道
  不适用”，不能显示为“已关闭”。

### 1.3 配置面与优先级

沿用现有三层来源：**装配显式 config > 环境变量 > `control.json` > 内置默认**。

| 层 | `contextFold` | `finalCheck` |
|---|---|---|
| 装配 config | `config.contextFold?: boolean` | `config.finalCheck?: boolean` |
| 环境变量 | `STREAM_AGENT_CONTEXT_FOLD=1\|0` | `STREAM_AGENT_FINAL_CHECK=1\|0` |
| `control.json` | `toggles.contextFold`（schema 3 → 4） | `toggles.finalCheck` |
| CLI | `dsh-stream-agent toggle context-fold on\|off` | `dsh-stream-agent toggle final-check on\|off` |
| 控制栏 `bar` | 新增 `C` 键切换（避开现有 1-4/l/?/r/q/u） | 新增 `F` 键切换 |
| 桌面控制页 | “上下文折叠”开关 + 影响提示 | “收束校验”开关 + 影响提示 |

迁移：`control.json` schema 3 读到 4 时，缺失的 `toggles` 按默认 `true` 补齐；升级不改变
任何现有会话的行为。旧字段 `mode` 的别名迁移逻辑保持不变。

### 1.4 对用户使用的影响

| 配置组合 | 上下文体积 | 请求数 | 缓存/换基 | 主要风险 |
|---|---|---|---|---|
| 折叠开 + 阈值已设 | 长会话增长受控 | 压缩本身不加请求 | 每次触发一次计划性换基，注入 `[tf-stream:context-rebased]`，下一次请求前缀变冷 | 换基配额用尽时压缩被跳过（记 `compaction-skipped`），不会静默 |
| 折叠开 + 阈值未设 | 与关闭相同 | 不变 | 无 | 用户以为“已省 token”，实际未触发；控制台必须显式提示 |
| 折叠关 | 只增不减（除非 `segmentMaxChars` 触发） | 不变 | 前缀最稳，无压缩换基 | 长会话单请求输入持续变大，可能撞模型窗口或供应商上限 |
| finalCheck 开 | 不变 | 可能多 1 次或多次收束/补证据请求（受 `closeOutRequests` 约束） | 无 | 交付更严格；未完成时用户会看到 `blocked` 或未完成说明 |
| finalCheck 关 | 不变 | 省去为 `tf-final` 追加的收束请求 | 无 | 占位/未验证内容可能被当交付；没有验收证据可追溯 |
| 两者都关 | 增长最快 | 最少 | 无压缩换基 | 省下的请求可能被更大的单请求输入抵消；长任务风险最高 |

建议的控制台文案（直接影响用户预期）：

- 折叠开关旁：`开启后仍需设置 maxInputTokens（压缩）与 effectElisionKeepRecent（效果折叠）才会生效；关闭会保留全部上下文，单请求更大但前缀更稳。`
- finalCheck 开关旁：`开启会在收束前检查 tf-final 与验收回执，可能多 1 次请求；关闭后流末正文直接交付，未验证内容不会被打回。`

## 2. 下一轮规划：请求装配权（结构性差异）

### 2.1 现状边界（为什么这是结构性差异）

当前插件只能改“宿主已经决定要发什么”之后的部分：

| 能做 | 不能做 | 代码事实 |
|---|---|---|
| 在追加区追加消息、整块丢弃旧段、压缩后计划性换基 | 改写 system 段、工具 schema、历史 `reasoning_content` 的回传策略 | `context-render.ts` 只做装配后断言；`render.ts` 的稳定段由宿主/插件协议共同决定 |
| 选择协议文本、是否默认带原生 `tools` schema | 在发送前按字段裁剪请求体；设置供应商缓存标记 | `nativeTools` 只控制插件自己的工具面，不等于请求装配权 |
| 前缀不单调时 fail-closed 或预算内换基 | 让宿主在 `llm/stream` 层接受一份重写后的历史 | `PrefixBrokenError` 是事后断言，不是事前装配接口 |

这导致省 token 的上限被卡在三处：固定前缀（协议/工具 schema）、历史回传（推理内容是否
必须全量带回）、以及无法按字段做请求预算。xuxiang 自有完整请求装配链，可以直接决定
“这次请求带什么、不带什么”；插件目前只能在宿主接缝处做减法。

### 2.2 目标与非目标

**目标**：在宿主允许的接缝内，获得一份“请求装配计划”能力，使插件能在发送前决定：

1. 本次请求携带哪些消息块（已压缩/已折叠/仅句柄）。
2. 是否携带原生工具 schema；若携带，能否按需裁剪描述。
3. 历史推理内容是否需要完整回传（受供应商契约约束，不能违反）。
4. 供应商缓存标记与稳定前缀的对齐方式。

**非目标**：

- 不 fork 宿主 loop，不替换 `llm/stream`，不改供应商协议。
- 不绕过前缀断言；任何装配计划仍须通过逐字节前缀校验，否则 fail-closed。
- 不改变工具语义与安全策略；不改 `tf-*` 协议的命令面。

### 2.3 规划条目（可追踪）

| ID | 条目 | 优先级 | 依赖 | 验收（可复算） | 状态 |
|---|---|---|---|---|---|
| **RA-0** | 宿主装配接缝探针：确认 `llm/stream` 是否拒绝改写历史（U1）、`systemPrompt.context` 替换语义（U10）、子调用会话事件（U4）、不依赖 preset id 判定 PTC（U3） | P0 | 宿主 `rc.3` | 4 份探针产物落 `eval/runs/`，每份含请求序列 diff 与结论；不成立项明确标注“结构不可对齐” | 下一轮 |
| **RA-1** | 定义 `AssemblyPlan`：`{ messages, tools, reasoningPolicy, cacheHints }`；宿主校验后再发送 | P1 | RA-0 | 契约文档 + dry-run；同一计划两次投影逐字节一致；0 前缀违规 | 下一轮 |
| **RA-2** | 字段级省略：工具 schema 按需裁剪、重复块省略、已折叠效果只留 `[applied pN]` | P1 | RA-1 | 同任务同模型：四分量 ≤ 基线，严格二分量 ≤ 基线，请求数不增加；逐请求字段字节可复算 | 下一轮 |

### 2.5 风险与不确定

- 宿主 `llm/stream` 若在发送前改写历史，插件侧装配会被再次改写，导致断言失真；
  RA-0 必须先确认。
- 字段省略可能触发供应商契约（带 tools 时历史推理须完整回传），不能把“省略”做成
  “违约”；该项以供应商文档与实测为准。
- `AssemblyPlan` 与宿主 `surfaceOp: replace` 的职责可能重叠，需在 RA-1 明确唯一事实源。
- 本文不主张“改写装配一定更省 token”；RA-2 的验收是双向口径都不高于基线，否则不采纳。

## 3. 前缀不一致发送 fail 的兜底确认（已确认）

### 3.1 判定与处置矩阵

代码入口：`loop.ts` `#assertWirePrefix`（约 4037 行）与 `render()` 内置 preflight。

| cause | 触发条件 | 处置 | 是否发送本次请求 | 是否让模型重发 |
|---|---|---|---|---|
| `append-drift`，预算内 | `prefixPolicy != 'fail'`；本回合 <1 次、本会话 <3 次；`auto` 或换基预算满足 | **受限换基**：记账 `prefix-reset`，重置基线，照常发送**同一份** `next` | 是，仅此一次 | **否**，不是模型重发，是同一请求放行一次 |
| `append-drift`，超预算或 `prefixPolicy='fail'` | 配额用尽 / 策略禁止 | fail-closed | 否 | 否 |
| `stable-drift` | 稳定段（首条）逐字节变化 | fail-closed，始终 fail，不受 `prefixPolicy` 影响 | 否 | 否 |
| `shrink`（越界） | 承诺前缀变短、历史被销毁 | fail-closed | 否 | 否 |
| `planned-rebase` | 压缩 / 通道切换 | 发送前已重置基线，不进入断言 | 是（正常路径） | 否 |

关键点：`append-drift` 的“放行”发生在**发送前**，比较对象是上一请求的承诺前缀；它不会
新开一次 API 调用，也不会把错误回灌给模型让它重写。

### 3.2 fail-closed 的兜底链

`#prefixFailClosed` → `#deliverFallbackFinal` → `stepEnd` → `blocked`：

1. **记账**：写 `prefix-broken` fault、ledger（cause/index/stablePrefixLen/expected/actual）、
   开发者 warn。
2. **最小对账**：pending 写入意图整批标 `unknown`；只解除恢复锁，**不重放工具、不声称回滚**
   （`#reconcilePendingIntents`）。
3. **兜底交付**：若本回合至少有一条 `ok` 命令，写一条 assistant 消息：
   - 开头明确 `[未完成交付] 回合在收束预算内停止…没有收到有效的 tf-final。以下为台账事实，不是模型结论`；
   - 最多列 8 条已完成命令（写/执行/读），最近一次命令输出尾部 ≤700 字符；
   - 列未完成/未验证命令；
   - 结尾提示“如需继续，请直接说明下一步”。
4. **收束**：`stepEnd`，`reason.kind='blocked'`，本回合结束。

用户看到的不是原始异常，也不是停在最后一句 prose；是一条明确标注未完成的交付说明。
零产出回合（没有任何 `ok` 命令）**不写**兜底消息，这是刻意“不伪造完成”，但也是当前
的用户可见缺口（见 §3.4）。

### 3.3 是否增加任务轮数

| 问题 | 结论 | 依据 |
|---|---|---|
| 会不会自动让模型重发？ | **不会**。没有“重发请求”路径；`append-drift` 只是同一份 `next` 放行一次 | `#assertWirePrefix` 的 `verdict:'ok'` 分支 |
| 会不会多一次 API 请求？ | **不会**。fail-closed 直接不发送；受限换基也是发送同一份，不新增请求 | 同上；`#prefixFailClosed` 无请求 |
| 会不会增加任务轮数？ | **不会自动增加**；本回合以 `blocked` 收束。用户要继续，需要自己再发一条消息，形成新回合 | `reason.kind='blocked'` + `break` |
| 是否影响后续成本？ | `append-drift` 放行会重置缓存基线，下一请求前缀变冷（成本约 C）；配额用尽后只能 fail-closed | `#noteCacheReset` / `resetCause='prefix-reset'` |

因此，“fail 是否兜底”的答案是：**有兜底，但不是自动重试**；它把“失败”转成“有事实的
未完成交付”，代价是本回合结束，而不是多几轮模型调用。

### 3.4 已知缺口

- 零产出回合没有兜底消息：界面可能停在最后一句 prose，只有台账/控制栏能看到 `blocked`。
  是否补一条“本回合未产生可交付事实”的用户消息，需要单独决策（会让“零产出”也有可见终态，
  但可能被误读为模型回答）。
- `append-drift` 的放行配额是“每回合 1 次/每会话 3 次”，用尽后同一类抖动会直接 fail-closed；
  配额是否应可配（当前是常量）未定。
- 兜底消息是台账事实，不是模型结论；用户若直接把它当答案，可能高估完成度。文案已明确
  标注“不是模型结论”，但控制台/桌面端的视觉层级仍需验收。

## 4. `tf-peek` 反复读取与准确性确认（已确认）

### 4.1 什么情况下会触发 peek

| 旋钮 | 默认 | 行为 | 是否增加 peek |
|---|---|---|---|
| `maxReadChars` | `0`（不限制） | 首读全文，不投索引 | **否**；代价是首个请求注入大 |
| `maxReadChars > 0` 且文件超限 | `0`（未设） | 只投行锚索引（每 200 行一个锚；索引预算 2000 字符，超出退化为符号名）+ 未投递区间；正文靠 `tf-peek` | **是**，按窗口取回 |
| `readFeedbackBudgetPerRequest > 0` | `0`（不限制） | 单请求多文件读取超预算时，超出部分只给“头 800 字符 + 句柄” | **是**，下一请求 peek 补全 |
| `selfReadFeedback` | `full`（0.5.1 起） | 写后自读也回灌全文 | **否**；若回退 `receipt` 则会增加 peek |
| `peekBudgetChars > 0` | `0`（不限制） | 每回合取回超限返回 `[budget]`，要求先 grep 或下回合继续 | **可能增加跨回合 peek** |

结论：**默认配置下不会因为索引而增加 peek**；一旦用户开启 `maxReadChars` 或
`readFeedbackBudgetPerRequest`，peek 次数会按设计上升。这不是回归，是用“后续取回”换
“首个请求体积”。

### 4.2 已有抑制机制

| 机制 | 行为 | 代码 |
|---|---|---|
| span 账本 | 同一 handle、同一区间、内容 hash 未变 → 只回 `[unchanged]` 一行，不重发正文 | `obs.ts` `peekWithLedger` |
| 部分重叠 | 只返回未投递的新增区间，附一行“已投递区间不重发” | 同上 |
| 行锚索引 | 每 200 行一个锚，优先顶层符号；列出未投递区间，模型不用猜已读范围 | `obs.ts` `renderReadIndex` |
| 取回预算 | 超 `peekBudgetChars` 返回 `[budget]`，不静默截断 | `loop.ts:4394-4511` |
| 符号/字符定位 | `symbol` ±40 行；`offset`/`query` 字符级续搜；`request:N` 别名 | `peekBySymbol` / `recallText` |
| 延迟重试 | 同流 handle 未就绪时延迟到流末 drain 后重试一次，不立即失败 | `#deferredPeeks` |

两个回退点会直接放大 peek 次数，控制台不应把它们当作“省 token 优化”默认开启：

- `spanLedger=false`：`peekWithLedger` 恒走 content 分支，`[unchanged]` 不生效，重复区间会
  重发正文。
- `peekIndex=false`：大文件回到 0.4.x 头部截断形态，不投索引；模型只能靠猜行号取回，
  更容易反复 peek。

### 4.3 会不会加大 peek 次数

**会，但有条件**：

- 开启索引（`maxReadChars>0`）后，大文件首读只给索引，模型必须至少 peek 一次才能看到
  正文；文件越大、目标越分散，k 越大。
- 开启单请求回灌预算后，多文件读取会被拆成“首批预览 + 后续 peek”。
- 取回预算耗尽时，模型被要求“先 grep 或下回合继续”，可能把一次取回拆成跨回合多次。
- span 账本只消除“同一区间重复读”，不消除“为了找目标而读多个不同区间”。

设计目标是 `k → 1`（`docs` 计划书 §7.1/§7.3），但当前没有强制“一次取回命中”的机制；
`k_mean ≤ 1.2`、`peek_requests_per_task ≤ 0.3 × 总请求` 仍是度量目标，不是保证。

### 4.4 准确性风险

| 风险 | 具体表现 | 现有缓解 | 残余风险 |
|---|---|---|---|
| 行号猜测 | 模型按 `from_line/to_line` 取回，行号偏了就拿错段 | 索引给行号 + 顶层符号；`symbol` 模式 ±40 行 | 200 行锚点之间可能没有目标符号，仍需多次试 |
| 索引粒度 | 每 200 行一个锚，目标落在锚点之间时索引不显示 | 未投递区间显式列出，模型可先 grep | 模型若不 grep，直接猜窗口，k 上升 |
| 快照陈旧 | handle 内容是读取时的快照；外部改文件后 peek 仍返回旧文 | 内容 hash 只校验 handle 内部，不校验磁盘 | 需要重新 `tf-read` 才能看到最新内容 |
| query 未命中 | 字面量不存在时返回“未命中 + 改用 grep/offset”，不是失败 | 明确引导，不触发错误重入 | 模型可能换多个 query 反复试，增加调用 |
| 预算截断 | 一次取回超预算被拒，模型需缩小范围或跨回合 | `[budget]` 明确文案 + 未投递区间 | 关键上下文可能被推迟到下一回合，影响一次成功率 |

### 4.5 建议

1. 默认保持 `maxReadChars=0`（全文首读），只在确有大文件、且首请求体积成为问题时开启索引。
2. 开启索引时同时设 `peekBudgetChars`，避免单回合无界取回；并保留 `tf-grep` 先行纪律
   （协议段已写“先 grep 后 peek ±40 行”）。
3. 需要“写后回验”省 token 时，优先用 `selfReadFeedback: 'receipt'` 回退点，而不是关
   span 账本；两者影响面不同。
4. 观测四个指标再决定是否调参：`k_mean`、`redundant_peek_ratio`、`peek_requests_per_task`、
   `deref_bytes/produced_bytes`（定义见计划书 §7.4）。
5. 不建议用“更密的索引锚点”直接换准确率：索引本身占首请求 token；应先看
   `redundant_peek_ratio` 是否真的高，再决定锚点密度。
