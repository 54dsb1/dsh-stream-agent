# ADR-001：长会话段边界 —— 整块丢弃（Whole-Block Discard）

- 状态：已采纳（0.3.0 实施，随 v0.4.0 规划 F7 交付）
- 决策日期：2026-11-16
- 影响范围：`src/kernel/render.ts`、`src/entry/loop.ts`、`docs/limitations.md`

## 背景

单流驱动器的稳定段（首条 system + 追加区）随任务增长单调追加——这是前缀缓存命中
的前提（C7：首条 system 逐字节冻结；追加区只增不改）。长会话（多任务连续 followup）
下追加区无界增长：输入 token 线性膨胀，最终任务的首请求会拖上全部历史。

v0.4.0 规划 F7 要求给出段边界方案，两条候选路线：

1. **整块丢弃**：旧段整体移出上下文，被丢弃原文句柄化（可按句柄回取），下一请求
   前缀重置——显式记录的缓存重置点。
2. **宿主压缩**：接受宿主 compaction 改写历史，压缩点作为新前缀起点，显式记录
   "缓存重置"。

## 决策

**采纳路线 1（整块丢弃），拒绝路线 2（宿主压缩）。**

理由：

1. **摘要式改写是红线**：压缩必然摘要/改写中间历史——这正是全项目禁止的
   （"禁止智能压缩/摘要"；模型事实一旦被改写，台账与上下文不再一致，排障与
   验收都失去依据）。宿主压缩的改写发生在插件视野之外，无法保证"改了什么"可审计。
2. **整块丢弃保持事实完整**：被丢弃的块原样保留在 obs 账本（句柄 `obs:read:seg-*`），
   `tf-peek` 按行段取回原文——"原文可按 request:N 回取"的落地形态。不摘要、不改写。
3. **边界可审计**：丢弃只发生在**完整回合边界**（新任务开始处），policyLog 显式记录
   （kind: segment-drop），台账同步（plugin:tf-agent/fault）。未记录的前缀不一致
   仍会被 render() 的 preflight fail-closed 拦截——这是唯一合法的前缀重置入口。

## 实现要点

| 要点 | 落地 |
|---|---|
| 触发条件 | 新回合开始（runTurn）且追加区字符数 > `segmentMaxChars`（缺省 160k ≈ 40k tokens；0/负数关闭） |
| 丢弃范围 | 追加区**头部**整块：从 0 到 `#segmentKeepFrom`（当前任务块起始下标）——即上一个已收束回合的全部块 |
| 块完整性 | 只丢整块，不拆块；工具调用与结果（同一回合内的 assistant 块与句柄增量）同进同出 |
| 原文回取 | 每个被丢弃块登记 obs（`obs:read:seg-t<turn>-<i>@v1`），`tf-peek`/`peekHandle()` 按行段取回 |
| 前缀语义 | `dropAppendHead()` 重置前缀基线（#lastStable = null）+ policyLog 记录；其余任何前缀不一致仍 fail-closed |
| 验收 | 100+ 请求 0 前缀违规；边界后首请求体积 ≤ 阈值 + 当前任务（末/首 ≤1.5× 断言见 test/f7-segment.test.ts） |

## 明确不做什么

- 不做摘要式压缩，不改写任何历史消息内容。
- 不在回合中间丢弃（当前回合的块永不丢弃——工具调用与结果不被拆开）。
- 不把"装配面缩小"或"丢弃"写成 token 收益：丢弃的收益是**长会话有界**，代价是
  一次显式缓存重置（下一条请求缓存未命中）；两者都在文档中如实呈现。

## 后果与已知限制

- 丢弃后的第一条请求是缓存冷请求（cacheWrite 重新计费）——这是"整块丢弃"路线的
  固有代价，发生频率受 `segmentMaxChars` 控制（阈值越高重置越少）。
- 多任务排队时（连续 pushUserTask 未 runTurn），段边界取**最后一个**任务块的起始
  下标；更早的排队任务块会被视为"旧段"丢弃（原文可回取）。需要跨任务连续上下文
  的用法应把多个目标放进同一条任务文本，而不是排队多条。
- `resumeIntentPolicy` / `segmentMaxChars: 0` 均为独立回退点；关闭段边界后长会话
  回到"追加区无界增长"的已知限制（docs/limitations.md）。
